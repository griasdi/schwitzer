## Target picture

- **Protocol rules.** `schwitzer-proto` owns every rule both sides apply to a task:
  - which stage a decision leads to (`Task::next_stage`);
  - which decisions a task offers (`Task::legal_decisions`, derived from `next_stage` in button order);
  - when a task is closed (`Stage::is_closed`);
  - whether it has a plan, and its open waits;
  - the lookup of a task by number (`RoomState::task`);
  - the "trim, then cut" rule for display text (`caps::clamp`).

  The server enforces these rules and the app shows them, and neither keeps a second copy.
- **Server.** `rpc.rs` validates shape and runs one transaction per mutation, and title and body go through `headline`. `store.rs` names each precondition once (`require_task_exists`, `require_open_task`, `require_stage`, `require_open_version`). It loads one task and a whole room with the same scoped queries. Its migrations are data (`MIGRATIONS`), and a test compares the migrated schema with a fresh one.
- **Release and update.** `schwitzer-release` owns everything about a GitHub release:
  - the parse of a release or a list, and the dev draft rule;
  - the archive kind per platform and its extraction;
  - the user agent, built from the program name.

  Callers keep only which release they choose and which asset they take.
- **Client.** The room state and the debug inbox belong to the client. The debug-session code lives in `debug.rs`, and a room's current debug session is read through one helper.
- **App core.** `app/mod.rs` is the Elm hub with one-line arms. Lifecycles live in their `impl App` files, including `fast_lane.rs` and `navigation.rs`. The open task's full-window sub-page (reading, history, suggestion) is one state, `TaskPage`. Resume and restart live in `resume.rs`, and the list's scroll API lives with the list.
- **App views.** Views compose widgets from `widgets.rs` (`byline`, `read_text`). Tokens, including the icon tint, are read only in `theme.rs`. Iced-free decisions live in `logic.rs`: the lamp, the wait candidates, copy texts and the shell-safe session id.
- **Agent integration.**
  - The fast lane has one rule set, `settings::Lanes`, which the app applies to its settings and to the MCP tools' copy alike, and one gate, `require_lane`.
  - The MCP tools build a task answer once, take stage and decision names from serde, and read debug folders through `debug.rs`.
  - The plugin has one helper for each repeated step: errors, JSON tool calls, joined projects, the claim marker and the build handoff. Its `TOOLS` mirror the Rust descriptions.
- **Docs.** ARCHITECTURE.md is the reference, and README, AGENTS.md, DESIGN.md and the diagrams agree with it. The diagrams carry no version numbers or counts that drift.

- `app/logic.rs` is about 1,900 lines with eight concerns. Recommendation: a `logic/` module with `tasks`, `omp`, `text`, `status` and `format` files behind the same `logic::` paths.
- AGENTS.md and ARCHITECTURE.md still describe the crates and app files twice, and this run updated both in many commits again. Recommendation, as in both earlier runs: AGENTS.md keeps commands, gate, headless and conventions, and points to ARCHITECTURE §3, §8 and §13.

## Remaining debt and risks

- `53e1f0f`: a failed comment resolve now goes through `Message::Failed`, which also drops a pending accept-return scroll. Both actions on one task within a few milliseconds are needed to see it.
- `e16df37`: `SessionDirs::received` drops a member folder whose listing fails part-way, where `debug_status` skipped only the failing entry before. This happens only on an I/O error inside the app's own debug folder.
- `dce57f0`: `install` builds the plugin bytes before creating the folder, so a serialization failure writes nothing.
- `0b37d70`: the plugin reads plan mode after the claim call instead of before it.
- `ef117c9`: build claims are kept under a new global key. An omp process that loaded the old plugin and then the new one does not see claims the old instance stored.
- `d61c2eb`: the MCP copy of the fast lanes is updated per change. A path that changes `settings.lanes` without `App::change_lanes` would leave the copy behind, and a future change of the lanes must go through that method.
- The plugin rewrite (`71210d2` to `ce11073`) marks every installed plugin out of date once. With `auto_update_plugins` on, the app rewrites it at once.
- Windows: `cargo.exe` clippy and app tests (with `self-update`) and the `schwitzer-release` tests ran after the release commits and on the final commit; all green. macOS code is not compiled here; CI checks it after the push. `ci.yml` changed (`739fe20`) and is exercised only by CI.
- Not seen on screen: switching room or project while a sub-page is open, an IPv6 server, and the debug page with received files.

## Starting points for the next phase

- A new stage or decision is one edit to `Task::next_stage` in proto; the buttons, the MCP `decisions` rows and the server follow it.
- A new store precondition or migration is one named helper or one `MIGRATIONS` entry.
- A new fast-lane rule is one `Lanes` method, applied through `App::change_lanes`.
- A new MCP tool that answers a task is `Tools::answer_task`.
- A new plugin command reuses `toolJson`, `requireJoined`, `reportError` and `markerLine`.
- `TaskPage` takes the next full-window sub-page of the open task as one variant.
