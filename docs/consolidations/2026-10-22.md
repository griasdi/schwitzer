## Target picture

- **App core (`app/mod.rs` and friends).** `mod.rs` is the Elm hub: `Message`, `App`, `update`, `view`, `subscription`. Each feature's lifecycle lives in its own `impl App` file (`resume.rs`, `plugins.rs`, `updates.rs`), and the iced-free decisions sit in `logic.rs`. The room list mirrored from `Client::rooms()` has one owner (`rooms.rs`) with lookups by `RoomId`. Pages, including the first-start page, are `Page` variants, not flags beside it.
- **App views and look.** Views compose a small set of shared widgets (`widgets.rs`: input, picker, chevron, fold button, lamps). Every colour, radius and control size is a token or style function in `theme.rs`. A style or row shape that exists twice exists once.
- **App logic and local services.** `settings.rs` owns `settings.toml`, its validation, home and folder paths, and atomic file writes. `wsl.rs` owns every Windows/WSL split. `sessions.rs` and `update.rs` have no platform branches beyond what their job needs.
- **Agent integration.** `mcp/tools.rs` shapes JSON from one task row and one argument parser. `omp_plugin.rs` writes only what the current plugin needs. The plugin README describes every command and prompt that `index.ts` has.
- **Client.** `schwitzer-client` is the only way to a room server. One lookup maps a room to its server. Rooms the server sends without a kept key stay tracked by server until they go stale.
- **Server.** Every mutation goes through one transaction helper (`rpc::in_room`) that commits and then publishes under the store lock. The store is private to the crate. Release announcement and auto-update share their GitHub code through `schwitzer-release`, not through each other.
- **Proto.** Wire types plus the small rules both sides must agree on (`Task::has_plan`, `caps::cut`, the short id). No dead aliases or public helpers without callers.
- **Release and update (new crate).** `schwitzer-release` holds the GitHub release lookup, asset digest, bounded download, sha256 check, tar.gz extraction and Unix swap. The app keeps zip, AppImage, the Windows swap and restart. The server keeps the release list, `AutoUpdate` and exec.
- **Tooling and docs.** Versions live in `[workspace.dependencies]`. `docs/ARCHITECTURE.md` is the reference, and AGENTS.md, README.md, PRODUCT.md, DESIGN.md, the plugin README, the SVGs and the site agree with it and with the code.

## Dropped

- #51 Four "Unexpected reply" arms: taste. They are defensive arms for a reply variant the server never sends. Unifying them with the lowercase `pick` text changes a message nobody sees, and the internal part saves one line per arm.
- #52 `expanded`/`reset_drafts()` helper: the call sites differ on purpose (reset on change, reset on close and on reopen, clear without reset after proposing). A single helper would either change behavior or need a flag per site.
- #53 `ProtoError`: merging it into the postcard error would change the "decoding failed: …" text that `ClientError::Proto` shows.
- #54 Plugin `rememberBuild`: `claimFor` has typed `number` and `project`, while `forward` reads them from the answer. A shared helper would take the project from the answer, whose casing can differ, and would skip remembering on a malformed answer.
- #55 Plugin tolerance for older `schwitzer.json`: the defaults (`?? []`, `=== true`) are the "malformed omp file is an error, never a crash" invariant applied to a file people can edit. Removing them makes a hand-edited file throw.
- #56 Trimming AGENTS.md to pointers into ARCHITECTURE.md: AGENTS.md is the first file coding agents read, and how much of the architecture it repeats is the maintainer's call. The drift it showed (#1) is fixed. See greenfield observations.
- #57 Removing `chosen_projects` from `resume_from_an_older_version_is_read`: that field simulates a `resume.json` written by an older version, which is the point of the test.
- Parts of findings left out as taste: the text_editor helper of #27 (a call would be as long as the chain it replaces), the form-row and path-row helpers of #30, the `FromBlob` and bind helpers of #40. Also left out: the two path-collecting plugin filters in `app/mod.rs` from #29, which use a different predicate.
- #43, kept part: `Entry.server` in the client stays. The server's backlog sends every room of the identity, including rooms whose key this client does not hold. A lookup over the kept keys would never drop those rooms when they go stale.

## Starting points for the next phase

- `schwitzer-release` is the one place to change how both updaters find, fetch and check a release.
- `rpc::in_room` makes a new room mutation one closure plus its event. `mutate_claim` shows how a reply without a task fits.
- `app/rooms.rs` is the one place for lookups by `RoomId` (ids computed once per reload), which views over several rooms (a cross-room inbox, per-room badges) can build on.
- `app/plugins.rs` and `plugin_config_for` are the single place for new `schwitzer.json` fields.
- `logic::next_check` makes update decisions testable without iced. More of `updates.rs` can follow the same pattern.
